# Synthetic Data Report: Day 3 Generation Run

**Generator:** `scripts/generate_synthetic_data.py`, configuration
`config/generator_v1.yaml` (frozen; hash below), master seed **42**
(`config/data_config.yaml`). Independently checked by
`scripts/verify_synthetic_data.py`. Reproducible from the Day 2 outputs
(`data/processed/*.csv`) with no other inputs.

**None of the entities described in this document are real Upwork
users.** Every worker, client, request-to-client assignment, interaction,
and rating below is synthetic, generated by this project's own generator.
The only real data involved is the 12,000 Day 2 sampled job postings
(`link`, category, skills, pay, country), which are demand-side records
from the Upwork Job Postings Dataset 2024 and are *assigned to* synthetic
clients rather than being clients themselves.

## 1. Why synthetic complementary data is necessary

The raw dataset (docs/experimental_design.md Section 2) has no worker
profiles, no client identifiers, no applications, hires, ratings, or
reviews, and only a 12-day effective collection window. A hybrid
recommender comparing content-based filtering, collaborative filtering,
and Knowledge Graph reasoning needs worker profiles, a client-worker
interaction history, and a time axis long enough to support a temporal
train/validation/test split -- none of which the raw data provides. This
generator supplies all three while keeping every attachment to real data
explicit and auditable.

## 2. Real vs. synthetic, at a glance

| Entity | Status | Grounding |
|---|---|---|
| The 12,000 sampled requests | **Real** | Day 2 `sampled_requests.csv`; `link` preserved unchanged |
| Category, skills, pay of each request | **Real** | Same Day 2 record |
| Clients | **Synthetic** | Country/category/activity distributions match the real request population; identities and taste are fabricated |
| Workers | **Synthetic** | Category allocation, skill pools, and pay grounded in real category-level distributions; identities, quality, taste, country are fabricated |
| Simulated timeline | **Synthetic** | Real `published_date` is not used (Section 2, Limitation 3) |
| Interactions (shortlist/hire), ratings | **Synthetic** | Generated by the latent-utility model in this document, not observed |

## 3. Client generation

2,000 clients (`C000001`-`C002000`). Per country (docs/experimental_design.md
Section 7):

1. **Client count per country** is apportioned from the real per-country
   share of the 12,000 sampled requests (largest-remainder, floor 1 -- a
   country with any requests gets at least one client) `[IMPL]`.
2. **Primary category** is drawn from that country's own request-category
   distribution.
3. **Activity level** (requests per client): a lognormal weight
   (mean 6, clipped to [1, 40]) is rescaled within each country so that
   client quotas sum exactly to that country's real request count.
4. **Assignment**: each client fills its quota, ~65% from real requests
   in its own primary category (`client_category_coherence`), the rest
   from any real request in the same country; any rounding leftover is
   assigned round-robin.
5. **Latent taste** `u_c ~ N(0, I_8)` -- generator-private, in
   `clients_private.csv`, never in `clients.csv`.

**Realised:** every one of the 12,000 requests is assigned to exactly one
client (verified disjoint/exhaustive); mean 6.0, min 1, max 40 requests
per client, matching the configured target exactly by construction.

## 4. Worker generation

3,000 workers (`W000001`-`W003000`), 300 of them (10%) the new-entrant
cold-start cohort (Section 8 below).

### 4.1 Category allocation

Workers per primary category are apportioned from each category's real
share of eligible Day 2 jobs (`category_stats.csv`), with a floor of 20
per category (docs/experimental_design.md Section 8). Realised: 88
categories, minimum 22 workers, matching the floor closely.

Each worker draws 0-2 secondary categories from the 5 categories most
similar to its primary category (`category_similarity.csv`, precomputed
in Day 2 from real skill co-occurrence).

### 4.2 Skills

True skills (generator-private, `workers_private.csv`) are sampled
without replacement from the **real** skill-frequency distribution of
the worker's primary category (5-12 skills), plus 1-3 from its secondary
categories' pools if any -- never uniformly from all 1,187 vocabulary
skills. Proficiency per true skill is Beta(2, 2), shifted upward by
experience level.

**Declared skills** (observable, `workers.csv`) are a noisy subset: true
skills with proficiency >= 0.4 are declared with probability 0.85,
weaker ones with probability 0.40, plus up to 2 "padding" skills (popular
category skills the worker does not truly hold), each with probability
0.30. Every declared and true skill is verified to be a member of the
Day 2 controlled vocabulary (1,187 skills) -- see
`tests/test_synth_integration.py`.

### 4.3 Experience and latent quality

Experience level (entry/intermediate/expert, target 40/40/20) and latent
quality `q_w` (generator-private) are drawn from a correlated bivariate
normal (target correlation 0.4), then experience is discretized by
quantile and quality is mapped through a Beta(2, 2) inverse-CDF. Realised
correlation between quality and (entry=0/intermediate=1/expert=2) on the
frozen run: **~0.37**, close to target given the discretization.

### 4.4 Rate and price tier

Rate and price tier are sampled *together* from the same real
(`price_tier`, `pay_amount`) pair within the worker's category
(`eligible_jobs.csv`), biased toward lower percentiles for entry-level
workers and higher for experts (a power-law bias on the uniform draw used
to pick the row) `[IMPL: exact bias exponents are an implementation
choice, not specified in the approved design]`. Because real fixed-price
budgets are heavy-tailed and never capped (docs/experimental_design.md
Section 3.5), a handful of workers in high-budget categories inherit very
high `rate` values -- this mirrors the real data's own dispersion rather
than being a generation error.

### 4.5 Country [ASSUMPTION: no real worker-location data exists]

Workers are sampled from the top 20 real client/job countries, with
shares smoothed by a square-root transform to reduce US dominance
(docs/experimental_design.md Section 8). A repair pass then guarantees at
least 10 eligible workers (matching category, primary or secondary) for
every (category, required-country) pair that appears in a
location-restricted sampled request. Realised: 131 such pairs checked, 64
were short of the floor, 272 worker-country reassignments made to satisfy
the guarantee.

## 5. Simulated timeline and temporal split

A 365-day simulated calendar (docs/experimental_design.md Section 7.6).
Each client has an activity start day `~ U(0, 330)`; its assigned real
requests get a simulated day uniformly drawn between that start day and
day 365. The train/validation/test split is a **global cut on this
simulated day**, not a random post-hoc split: the first 8,400 requests
by simulated day are training, the next 1,200 validation, the last 2,400
test -- exactly 70.0% / 10.0% / 20.0% because 12,000 divides evenly.

| Split | Count | Day range |
|---|---|---|
| Train | 8,400 | 5.84 - 323.01 |
| Validation | 1,200 | 323.02 - 336.80 |
| Test | 2,400 | 336.81 - 364.99 |

No validation/test request's simulated day precedes any training
request's; verified in both the test suite and the independent verifier.

## 6. Multi-factor latent utility model

### 6.1 Formula

```
U(c, w, r) = β_S·S̃ + β_T·T̃ + β_Q·Q̃ + β_B·B̃ + β_C·C̃ + ε,   ε ~ N(0, σ²)
```

| Component | Definition | Weight (frozen default) |
|---|---|---|
| `S` true skill fit | mean over the request's required vocabulary skills of `max(p_w(s), 0.5·max_{s'∈N(s)} p_w(s'))`, `N(s)` = top-10 NPMI neighbours from Day 2's full-corpus co-occurrence table | 0.30 |
| `T` taste | `u_c · v_w / √8` | 0.25 |
| `Q` quality | `q_w` | 0.20 |
| `B` budget fit | 1 if worker price tier ≤ request price tier + 0.1, else `exp(-5·excess)`; 0.7 if request pay unspecified | 0.15 |
| `C` category fit | 1.0 primary match, 0.6 secondary | 0.10 |

Each raw component is standardized (`S̃ = (S - mean)/std`) using moments
estimated in Pass 1 (below) before combination. Noise `σ` is calibrated
so it contributes ~20% of total utility variance
(`utility_noise_variance_share`); realised `σ = 0.244` against a realised
signal variance of 0.237.

### 6.2 Two-pass generation [IMPL]

The approved design standardizes utility "across all generated
request-applicant pairs" -- a global quantity -- while hire outcomes
depend on worker capacity, which depends on *prior* hire outcomes in
simulated time. Standardizing live during a capacity-aware chronological
pass is circular. This generator resolves it in two passes:

- **Pass 1** (`estimate_utility_moments`): every request's eligible pool
  is built *ignoring* capacity (capacity is the only eligibility factor
  that depends on simulation state; category/join-day/location do not),
  applicants are sampled with the real self-selection weighting, and
  their raw components are accumulated to obtain global mean/std per
  component, the realised signal variance, and the shortlist-level
  `max U` distribution used to calibrate the hire-probability threshold
  (`theta`) to the target 85% hire rate via bisection.
- **Pass 2** (`simulate`): the actual chronological simulation, with real
  hire-capacity tracking (a rolling 30-day, max-4-hires window per
  worker), standardizing every pair with Pass 1's frozen moments.

Realised hire rate: **84.7%** (target 85%; the ~0.3 point gap is the real
effect of capacity exclusions, which Pass 1 does not model).

### 6.3 Anti-circularity and variable classification

No generator factor is a single recommender's scoring rule (docs
Section 9.1): `S` uses proficiency-weighted coverage with related-skill
partial credit, a different functional form from any similarity measure
a CBF/KG method would compute; `T` is invisible to CBF entirely; hires
are *sampled* (Plackett-Luce shortlist, then a second stochastic draw),
never `argmax`.

| Class | Fields | Where |
|---|---|---|
| Observable profile/request | `declared_skills`, `experience_level`, `price_tier`, `rate`, `country`, `primary_category`, `secondary_categories`, `join_day` | `workers.csv`, `clients.csv`, `requests.csv` |
| Historical interaction | `interactions.csv` (SHORTLISTED/HIRED events), `ratings.csv` | Derived only from training-period events once modelling begins (Day 4+) |
| Generator-private latent | `quality`, `true_skills`, `proficiency`, worker/client `taste_*` | `workers_private.csv`, `clients_private.csv` |
| Evaluation truth | raw/standardized `S/T/Q/B/C`, `noise`, `utility`, `is_hired` | `truth.csv` |

## 7. Cold-start design

A stratified random 10% of workers (300, by primary category,
`select_cold_start_cohort`) have `join_day` set to the simulated day of
the **first validation-period request** (323.02), not day 0. The
chronological simulation's eligibility filter (`join_day <= request
day`) therefore never places them in a training-period applicant pool --
**by construction**, not by deleting any generated history. Verified: 0
cold-start-worker interactions among training-split events, in both the
test suite and the independent verifier. They enter normally from the
first validation request onward, on equal terms with established
workers.

## 8. Interaction generation

Per request: an eligible pool (category + join day + location, capacity
in Pass 2) is built, up to 30 applicants self-select via skill-fit
weighting (`0.3 + S(r, w)`), a 5-member shortlist is drawn via
Plackett-Luce sampling of utility, and one shortlisted worker is (with
calibrated probability) hired via a second, sharper Plackett-Luce draw.
**`HIRED` is the primary implicit-feedback event for collaborative
filtering**; `SHORTLISTED` (without hire) is a weaker positive signal
kept for graded relevance (docs/experimental_design.md Section 15:
hired=2, shortlisted=1, otherwise 0).

**Candidate-pool statistics** (ignoring capacity, all 12,000 requests):
mean 85.6, median 84, min 5, max 193; 719 requests (6.0%) have a pool
below 20 candidates -- these are niche categories near the 20-worker
floor and are flagged for later evaluation-methodology attention (docs
Section 15 already excludes eligible pools below 20 from evaluation).

**Realised totals:** 60,000 interaction rows (5 per request x 12,000),
10,163 hires (84.7%), 49,837 shortlisted-not-hired.

## 9. Ratings

Conditional on `HIRED` only, with a 90% completion probability
(realised: 90.3%, 9,173 ratings). Rating is
`r* = 0.5·Q̃ + 0.3·S̃ + 0.2·B̃ + N(0, 0.5²)` (weights from
`rating_weights`), mapped to 1-5 via quantile thresholds calibrated on
this run's realised `r*` distribution to target the documented J-shape.
Realised distribution: 65.0% five-star, 20.0% four-star, 10.5% three-
star, 3.0% two-star, 1.5% one-star -- matching the ~65/20/15 target
closely. Ratings are never a deterministic transform of `quality` alone;
they mix three standardized truth components plus independent noise.

## 10. Sparse-history threshold

Computed once, after generation, from **training-split hire counts among
established (non-cold-start) workers only**, as the 33rd percentile
(docs/experimental_design.md Section 12): realised **N = 1** (median 2,
mean 2.64, max 19 across 2,700 established workers). Frozen here; not
re-derived or tuned once any recommender is built.

## 11. Leakage controls

| Risk | Control | Verified by |
|---|---|---|
| Latent quality/taste reaching a model-visible file | Kept exclusively in `*_private.csv`; column-name disjointness enforced | `tests/test_synth_leakage.py`, `scripts/verify_synthetic_data.py` |
| Utility score itself exposed | Lives only in `truth.csv` (generator-private) | Same |
| Cold-start workers acquiring training history | `join_day` gate is structural, not a post-hoc filter | `tests/test_synth_integration.py::test_cold_start_workers_have_no_training_interactions` |
| Future interactions influencing training-period state | Capacity tracking and all derived stats (sparse threshold) use only `split == "train"` rows | Same suite |
| Skill relatedness shared between generator and future KG edges | Generator's `S` uses Day 2's **full-corpus** co-occurrence table; a future Knowledge Graph should use the **background-corpus** table instead (Day 2 already produced both, separately) | Design note carried from docs/experimental_design.md Section 14 |
| Mixture ground truth favouring a future hybrid | Two frozen sensitivity variants (`generator_v1_content_leaning.yaml`, `generator_v1_collaborative_leaning.yaml`) exist for later comparison; not run today | Section 12 below |

## 12. Sensitivity-analysis configurations

`config/generator_v1_content_leaning.yaml` (β_S 0.50, β_T 0.10, β_Q 0.15,
β_B 0.15, β_C 0.10) and `config/generator_v1_collaborative_leaning.yaml`
(β_S 0.15, β_T 0.45, β_Q 0.20, β_B 0.10, β_C 0.10) exist so that any
conclusion drawn under the balanced default can later be checked for
robustness to the weight configuration, rather than being an artefact of
one choice (docs/experimental_design.md Section 14). Neither is designed
to make any particular future recommender win; both were smoke-tested
end-to-end during Day 3 (confirmed to run and produce a valid dataset,
~85% hire rate) but their outputs were **not** kept -- only
`config/generator_v1.yaml`'s dataset is the frozen Day 3 deliverable.
Running and evaluating them is deferred to whenever the later sensitivity
analysis is actually needed.

## 13. Limitations

1. Country, experience level, and latent quality/taste have no real-data
   equivalent; they are documented modelling assumptions, not observed
   Upwork attributes (Sections 4.3, 4.5).
2. The candidate-pool cap (150 workers, subsampled uniformly when a
   category's eligible pool exceeds it) is an implementation efficiency
   measure; it is generous relative to the 30-applicant/5-shortlist
   sizes actually used, so it should not materially affect dynamics, but
   it is a deviation from "score every eligible worker."
3. Pass 1's hire-rate calibration ignores capacity exclusions, producing
   a small (~0.3 point) gap between the calibrated target and the
   realised hire rate.
4. The rate/price-tier bias-by-experience exponents (Section 4.4) are an
   implementation choice, not a value specified in the approved design.
5. As in Day 2, all conclusions drawn from this dataset describe
   performance within this constructed experimental environment only.

## 14. Reproducibility

- Master seed **42**; every generation stage draws from an independent
  child stream (`src/data/synth_rng.py`, `numpy.random.SeedSequence(42).spawn(...)`,
  named stages appended-only so future stages cannot perturb existing
  ones).
- Two independent full runs of `scripts/generate_synthetic_data.py`
  produced byte-identical `workers.csv`, `interactions.csv`, and
  `truth.csv` (verified with `DataFrame.equals`).
- `manifest.json` (both output directories) records SHA-256 hashes, byte
  sizes, and row counts per file, with relative POSIX paths.
- `config/generator_v1.yaml.sha256` records the frozen configuration's
  hash (see Section 15).
